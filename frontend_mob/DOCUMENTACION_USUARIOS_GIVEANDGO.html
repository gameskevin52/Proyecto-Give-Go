1. ¿Qué hace el módulo de usuarios?

El módulo de usuarios es el núcleo de autenticación y gestión de cuentas de Give&Go. Aquí se controla quién puede entrar al sistema, cómo se registra, cómo se actualiza su perfil, cómo se consulta la información personal y cómo el administrador puede listar o eliminar usuarios.

En el backend, todas estas funciones están en el archivo backend/src/controllers/userController.ts y las rutas se exponen desde backend/src/routes/userRoutes.ts.

3. Middleware y validaciones que se ejecutan antes de cada función

validateLogin
Valida que correo sea un email real y que password no venga vacío.
validateRegister
Valida nombre, apellido, rol, correo y longitud mínima de contraseña.
authenticateJWT
Revisa el Authorization: Bearer <token> o la cookie token. Si no existe o está vencido, responde con 401 o 403.
authorizeRoles('Admin')
Permite la acción solo si el usuario tiene rol administrador.

4. Función 1: login

POST /api/users/login

Botón o acción en frontend: Botón “Iniciar sesión” de la pantalla de login.

Request

POST /api/users/login
Content-Type: application/json

{
  "correo": "ana@gmail.com",
  "password": "123456"
}

Qué hace el backend

  • Lee correo y password desde req.body.
  • Busca el usuario con UsuarioModel.getByEmail(correo).
  • Si no existe responde 404.
  • Si el usuario está inactivo responde 403.
  • Compara la contraseña con bcrypt usando comparePassword.
  • Si coincide genera un JWT con generateToken().
  • Guarda la sesión en cookie opcional y registra auditoría.

Response exitoso

{
  "success": true,
  "message": "Sesión iniciada correctamente.",
  "data": {
    "user": {
      "id": "1",
      "rol": "voluntario",
      "nombre1": "Ana",
      "correo": "ana@gmail.com"
    },
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
  }
}

Response fallido

{
  "success": false,
  "message": "La contraseña es incorrecta.",
  "errors": []
}
Importante: El login no solo valida la contraseña; también genera el token que se usará en las siguientes pantallas y en las peticiones protegidas.

5. Función 2: register

POST /api/users/register

Botón o acción en frontend: Botón “Crear cuenta”, “Registrarse”, o “Registrarme”.

Request

POST /api/users/register
Content-Type: application/json

{
  "rol": "beneficiario",
  "nombre1": "Luis",
  "apellido1": "García",
  "correo": "luis@gmail.com",
  "password": "123456",
  "telefono": "3001234567",
  "barrio": "Usaquén",
  "ciudad": "Bogotá"
}

Qué hace el backend

  • Valida que el rol sea uno permitido: admin, voluntario, beneficiario, organizacion.
  • Consulta si ya existe un usuario con ese correo.
  • Si ya existe responde 409 Conflict.
  • Encripta la contraseña con hashPassword().
  • Guarda el nuevo usuario en la base de datos.
  • Genera un JWT para iniciar sesión automáticamente.
  • Registra un log de auditoría.

Response exitoso

{
  "success": true,
  "message": "Usuario registrado con éxito.",
  "data": {
    "user": {
      "id": "2",
      "rol": "beneficiario",
      "nombre1": "Luis",
      "correo": "luis@gmail.com"
    },
    "token": "eyJ..."
  }
}

Response fallido

{
  "success": false,
  "message": "El correo ya está registrado por otro usuario.",
  "errors": []
}

6. Función 3: forgotPassword

POST /api/users/forgot-password

Botón o acción en frontend: Botón “Recuperar contraseña” o enlace “¿Olvidaste tu contraseña?”.

Request

POST /api/users/forgot-password
Content-Type: application/json

{
  "correo": "luis@gmail.com",
  "nuevaPassword": "nuevacontraseña123"
}

Qué hace

  • Busca el usuario por correo.
  • Si existe y viene una nueva contraseña, la encripta y actualiza.
  • Si no se envía contraseña, responde con verificación del correo.

Response exitoso

{
  "success": true,
  "message": "Contraseña restablecida correctamente. Ya puedes iniciar sesión con tu nueva contraseña.",
  "data": {
    "correo": "luis@gmail.com"
  }
}

7. Función 4: getProfile

GET /api/users/profile

Botón o acción en frontend: Botón “Mi perfil”, o carga automática al entrar a la pantalla de perfil.

Request

GET /api/users/profile
Authorization: Bearer eyJhbGciOi...

Qué hace

  • Valida el JWT usando authenticateJWT.
  • Obtiene el ID del usuario desde req.user.id.
  • Busca el usuario en la base de datos.
  • Devuelve el perfil completo limpio, sin mostrar la contraseña.

Response

{
  "success": true,
  "message": "Perfil recuperado.",
  "data": {
    "id": "1",
    "rol": "voluntario",
    "nombre1": "Ana",
    "correo": "ana@gmail.com",
    "telefono": "3001112233",
    "ciudad": "Bogotá"
  }
}

8. Función 5: updateProfile

PUT /api/users/profile

Botón o acción en frontend: Botón “Guardar cambios” en la pantalla de edición del perfil.

Request

PUT /api/users/profile
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{
  "telefono": "3210001234",
  "barrio": "Chapinero",
  "ciudad": "Bogotá",
  "biografia": "Me gusta ayudar a la comunidad",
  "password": "nuevaclave123"
}

Qué hace

  • Lee los datos enviados por el formulario.
  • Arma un updateData con solo los campos que vienen definidos.
  • Si llega una contraseña, la encripta antes de guardar.
  • Actualiza el usuario en la tabla principal.
  • Si el usuario es una organización, también sincroniza la tabla organizaciones.
  • Guarda auditoría del cambio.

Response

{
  "success": true,
  "message": "Perfil actualizado correctamente.",
  "data": {
    "id": "1",
    "rol": "voluntario",
    "telefono": "3210001234",
    "barrio": "Chapinero"
  }
}

Request

16. Flujo completo del usuario desde el botón hasta la base de datos

  1. El usuario hace clic en “Registrarse” o “Iniciar sesión”.
  2. El frontend prepara un JSON y lo envía al backend.
  3. La ruta recibe la petición y ejecuta el middleware de validación.
  4. El controlador consulta el modelo del usuario.
  5. El modelo hace una consulta SQL a MySQL.
  6. El backend responde con JSON y, si aplica, con JWT.
  7. El frontend guarda el token y redirige o actualiza la vista.
Frontend → Ruta → Middleware → Controller → Model → Base de Datos → Response JSON

18. Archivos exactos que intervienen y flujo completo desde el arranque

18.1. Arranque del servidor

  • backend/src/server.ts: es el punto de entrada de la API. Aquí se llama a initDB() para conectarse a la base de datos, luego se monta Vite en desarrollo y por último se ejecuta app.listen().
  • backend/src/app.ts: configura Express, CORS, JSON, cookies, middlewares de seguridad y monta todas las rutas bajo /api.
  • backend/src/config/db.ts: configura la conexión MySQL y prepara el fallback a memoria si MySQL no responde.

18.2. Registro de rutas del módulo usuarios

  • backend/src/app.ts: tiene la línea app.use('/api/users', userRoutes);.
  • backend/src/routes/userRoutes.ts: define todas las rutas del usuario, por ejemplo:
    router.post('/login', validateLogin, UserController.login);
    router.post('/register', validateRegister, UserController.register);
    router.get('/profile', authenticateJWT, UserController.getProfile);
    router.get('/', authenticateJWT, authorizeRoles('Admin'), UserController.getAll);

18.3. Validación antes de entrar a la lógica

  • backend/src/validators/userValidator.ts: en validateLogin y validateRegister se comprueban los campos obligatorios y el formato del correo.
  • Si falla la validación, el backend responde con un 400 o mensaje de error antes de cualquier lógica de negocio.

18.4. Protección con JWT

  • backend/src/middlewares/authMiddleware.ts: el middleware authenticateJWT toma el token del Authorization o de la cookie.
  • Hace verifyToken(token) y, si es válido, asigna req.user con id, rol y correo.
  • authorizeRoles('Admin') restringe rutas como listado, creación o eliminación de usuarios.

18.5. Lógica principal del usuario

  • backend/src/controllers/userController.ts: aquí está toda la lógica real de usuarios.
  • Se encuentra la función login, la función register, la función getProfile, updateProfile, getAll, delete, etc.
  • Dentro de esas funciones se usan helpers como mapUserToFrontend(), hashPassword(), comparePassword() y generateToken().

18.6. Capa de acceso a datos

  • backend/src/models/usuarioModel.ts: es la capa que consulta y modifica la base de datos.
  • Ejemplos reales: getByEmail(), getById(), getAll(), create(), update() y delete().
  • La capa del controlador no consulta directo la BD; primero llama al modelo.

18.7. Flujo real desde que presiona “Iniciar sesión”

Usuario hace clic en botón de login
  ↓
frontend_web/src/contexts/AuthContext.tsx
  ↓
login(correo, password)
  ↓
UserService.login(...)
  ↓
POST /api/users/login
  ↓
backend/src/routes/userRoutes.ts
  ↓
validateLogin
  ↓
UserController.login
  ↓
UsuarioModel.getByEmail(correo)
  ↓
comparePassword(password, user.password)
  ↓

  ↓

  ↓

  ↓
La app queda logueada y ya puede navegar a pantallas protegidas

18.10. Flujo real de actualización y eliminación

Usuario o admin edita perfil o elimina cuenta
  ↓
Frontend envía PUT/DELETE con Authorization
  ↓
authenticateJWT verifica JWT
  ↓
UserController.updateProfile o UserController.delete
  ↓
UsuarioModel.update o UsuarioModel.delete
  ↓
Se actualiza la base de datos
  ↓
Se genera auditoría con logAudit
  ↓
Se responde con success: true o 404/403/401 según el caso

18.11. Archivos visuales del frontend

  • frontend_web/src/contexts/AuthContext.tsx: guarda la sesión, maneja login, register, logout y updateProfile.
  • frontend_mobile/src/store/auth/AuthContext.tsx: hace la misma lógica en React Native con AsyncStorage.
  • La parte visual se hace en pantallas o componentes tipo Login, Register, Profile, Dashboard, UserList, etc.

18.12. Orden exacto del proceso completo

  1. Se inicia el servidor con backend/src/server.ts.
  2. Se carga la configuración de la BD con backend/src/config/db.ts.
  3. Se monta la app en backend/src/app.ts.
  4. Se registran rutas en backend/src/routes/userRoutes.ts.
  5. El frontend llama a la API desde autenticación.
  6. Las validaciones corren desde backend/src/validators/userValidator.ts.
  7. Los middlewares de JWT ejecutan backend/src/middlewares/authMiddleware.ts.
  8. La lógica del negocio vive en backend/src/controllers/userController.ts.
  9. El modelo entra en backend/src/models/usuarioModel.ts y hace consultas SQL.
  10. La respuesta vuelve en JSON al frontend.
  11. El frontend guarda la sesión y actualiza la interfaz visual.
  12. La operación termina con el usuario dentro del sistema o con un error controlado.
