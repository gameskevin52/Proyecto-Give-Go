Guía de Puesta en Marcha y Variables (.env)

El proyecto unifica el servidor Backend API y el cliente Frontend Web en un mismo proceso sobre el puerto 3000 (Express + middleware de Vite en desarrollo), mientras que la aplicación móvil se ejecuta de forma independiente con Expo.

Paso 1: MySQL (XAMPP)

1. Base de Datos

  1. Abre XAMPP Control Panel e inicia Apache y MySQL.
  2. Entra a http://localhost/phpmyadmin.
  3. Crea la base de datos: giveandgo_v2.
  4. Importa database/giveandgo_full_xampp.sql (el backend también aplica migraciones automáticas como publico_objetivo al arrancar).
BD: giveandgo_v2 | Puerto: 3306
Paso 2: Servidor Full-Stack

2. Web + Backend API

Desde la raíz del proyecto:

npm install
npm run dev

En modo producción:

npm run build
npm run start
Web: :3000 | API: :3000/api
Paso 3: App Móvil

3. Frontend Móvil (Expo 52)

Instala dependencias (incluye expo-location para GPS) y arranca Metro:

cd frontend_mobile
npm install
npx expo start

También disponible desde raíz con npm run mobile.

Conexión Clientes ➔ API REST

La Web utiliza apiFetch en frontend_web/src/services/db.ts leyendo el JWT de localStorage. La App Móvil utiliza apiClient (Axios) en frontend_mobile/src/services/api/apiClient.ts con interceptor Bearer desde AsyncStorage.

Conexión Backend ➔ Persistencia Dual

backend/src/config/db.ts intenta conectar a MySQL (giveandgo_v2) con timeout de 2 segundos y ejecuta migraciones automáticas. Si no hay servidor MySQL local, activa sin errores el respaldo persistente en backend/src/data/fallback_db.json.

Convención de Colores y Segmentación en Mapa (Web y Móvil)

Rojo: Ubicación GPS actual
Verde: Eventos Beneficiarios
Azul: Eventos Voluntarios
Morado: Sedes de ONG

Regla por rol: Un Beneficiario ve únicamente su ubicación GPS (rojo) y eventos para beneficiarios (verde); un Voluntario ve GPS, eventos para voluntarios (azul) y sedes (morado); Admin / Organización ven todo.

Prueba 1: Compilación, Tipado y Arranque Limpio (Terminal)

Obligatoria primero
  1. En la raíz del proyecto ejecuta npm run lint.
  2. Ejecuta npm run build para generar el bundle de producción Web y Backend.
  3. Ejecuta npm run dev para levantar el servidor local.
Qué debe salir para que esté bien:
  • npm run lint termina sin líneas de error (exit code 0).
  • npm run build genera dist/server.cjs y el compilado de frontend_web sin errores.
  • npm run dev muestra Servidor Give&Go iniciado correctamente con Backend en http://localhost:3000/api y Web en http://localhost:3000, sin errores rojos en consola.

Prueba 2: Integridad de Base de Datos (phpMyAdmin / MySQL Workbench)

  1. Enciende MySQL en XAMPP y asegúrate de tener DB_HOST=localhost y DB_NAME=giveandgo_v2 en .env.
  2. Ejecuta npm run dev y revisa en consola que diga Conectado exitosamente a MySQL en localhost:3306 (Base de datos: giveandgo_v2).
  3. En phpMyAdmin / MySQL Workbench ejecuta la consulta de verificación:
SHOW TABLES FROM giveandgo_v2;
DESCRIBE eventos;
SELECT id_evento, nombre, publico_objetivo, vacantes_voluntarios, vacantes_beneficiarios FROM eventos;
Qué debe salir para que esté bien:
  • Deben existir las tablas principales (usuarios, organizaciones, eventos, postulaciones, donaciones, donaciones_monetarias, donaciones_objetos, solicitudes, solicitudes_verificacion, categorias, auditorias).
  • La tabla eventos debe mostrar la columna publico_objetivo con valores 'ambos', 'beneficiarios' o 'voluntarios'.

Prueba 3: API REST, Reglas de Negocio y Seguridad RBAC (Postman)

  1. Crea un Environment con baseUrl = http://localhost:3000/api.
  2. Prueba A (Rutas Públicas): envía GET {{baseUrl}}/health, GET /events, GET /organizations, GET /categories y GET /donations sin token.
  3. Prueba B (Sin Autenticación): envía GET {{baseUrl}}/users, GET /audits y GET /verifications sin header Authorization.
  4. Prueba C (Login y Público Objetivo): haz POST {{baseUrl}}/users/login como Administrador, guarda el token, luego crea un evento con "publicoObjetivo": "beneficiarios" y consulta GET /events/:id.
  5. Prueba D (Aislamiento RBAC): registra o inicia sesión como Voluntario y envía con su token GET /users, GET /audits, GET /verifications, POST /events y DELETE /donations/1.
Qué debe salir para que esté bien:
  • Prueba A: todas responden 200 OK con "success": true.
  • Prueba B: todas responden 401 Unauthorized (nunca 200).
  • Prueba C: login devuelve 200 OK + token JWT; el evento creado devuelve 201 Created con vacantesVoluntarios: 0 automático cuando es exclusivo para beneficiarios.
  • Prueba D: todas las acciones de Admin/Organización ejecutadas con token de Voluntario devuelven 403 Forbidden.

Prueba 4: Flujos Web y Mapa Interactivo por Rol (Playwright / Navegador)

  1. Abre http://localhost:3000/login (o corre Playwright con geolocalización simulada). Verifica visualmente que no exista ningún botón ni tarjeta de acceso rápido de pruebas.
  2. Inicia sesión como Beneficiario y abre Mapa permitiendo ubicación al navegador.
  3. Cierra sesión, entra como Voluntario y abre Mapa; luego repite como Organización y como Administrador.
  4. En Playwright automatizado: npm init playwright@latest y ejecuta tu suite con npx playwright test.
Qué debe salir para que esté bien:
  • Login: formulario limpio sin credenciales precargadas ni botón de acceso rápido.
  • Beneficiario en Mapa: marcador Rojo en su GPS actual y únicamente marcadores Verdes (eventos para beneficiarios); 0 sedes moradas y 0 eventos azules.
  • Voluntario en Mapa: marcador Rojo (GPS), marcadores Azules (eventos voluntarios) y Morados (sedes ONG).
  • Admin / Organización: ven todos los marcadores (Rojo, Verde, Azul y Morado) y sus respectivos paneles sin mezclar herramientas de otros roles.

Prueba 5: App Móvil, GPS Real y Dashboards (Expo Go + Maestro)

  1. Ejecuta cd frontend_mobile && npm install && npx expo start y abre la app en Expo Go (teléfono físico o emulador con API apuntando a la IP local).
  2. Verifica el Login móvil: no debe existir la sección de cuentas rápidas de prueba.
  3. Entra al Mapa, primero rechaza el permiso GPS para probar el manejo de error, y luego concédelo desde Ajustes o el botón de activar GPS.
  4. Prueba el dashboard de cada rol (Admin 7 pestañas, Organización 3 pestañas + aprobar beneficiarios, Voluntario 3 pestañas, Beneficiario 2 pestañas + retirar postulación).
Qué debe salir para que esté bien:
  • Al rechazar el permiso GPS aparece un mensaje claro con opción de reintentar / abrir ajustes sin cerrar ni trabar la app.
  • Al conceder el permiso, aparece el pin Rojo en la ubicación real del teléfono y se recalculan las distancias en km en las tarjetas.
  • Cada rol muestra únicamente sus pestañas y funciones permitidas, sin errores rojos de React Native ni pantallas en blanco al abrir modales.

Prueba 6: Carga, Rendimiento y Seguridad (k6, Lighthouse y OWASP ZAP)

  1. Lighthouse: Con npm run build && npm run start, abre Chrome en Incógnito ➔ F12 ➔ pestaña Lighthouse ➔ Analyze page load.
  2. k6: Ejecuta k6 run load-test.js con 20 usuarios virtuales durante 30 segundos sobre GET http://localhost:3000/api/events.
  3. OWASP ZAP: Ejecuta Automated Scan sobre http://localhost:3000.
Qué debe salir para que esté bien:
  • Lighthouse: Performance y Best Practices ≥ 85/100 y 0 errores graves en consola.
  • k6: http_req_failed < 1% y percentil p(95) < 300ms en todas las peticiones.
  • OWASP ZAP: 0 alertas de riesgo Alto (High) y cabeceras de seguridad activas gracias a helmet.
